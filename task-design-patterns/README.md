# Домашка: Design Patterns & Principles

## Task 1 — SOLID: знайди і виправ
Старий клас `ReportManager` порушував два правила SOLID:

1. **SRP (Єдина відповідальність)**
   Клас робив тупо все підряд: перевіряв дані, генерував текст (під PDF чи CSV), зберігав у файл і відправляв на пошту. Це занадто багато для одного класу.
   **Як я пофіксив:** Розніс логіку по різних класах. Тепер є `ReportValidator` для перевірок, `ReportFormatter` для форматування і `ReportDelivery` для відправки/збереження. Кожен клас робить тільки одну свою справу.

2. **OCP (Відкритість/Закритість)**
   Щоб додати новий формат звіту (наприклад, XML), треба було б лізти прямо в код `ReportManager` і дописувати новий `else if`.
   **Як я пофіксив:** Зробив інтерфейс `ReportFormatter`. Тепер, якщо треба додати новий формат, я просто створю новий клас, який імплементить цей інтерфейс. І старий клас взагалі не доведеться чіпати. Те ж саме зробив із способами доставки через інтерфейс `ReportDelivery`.

## Task 4 — Pattern: Builder (свій патерн)
- **Патерн:** Builder (Будівельник)
- **Категорія:** Твірний 
- **Що він вирішує:** Допомагає створювати складні об'єкти крок за кроком. Це рятує від "кілометрових" конструкторів з купою параметрів, де половина значень зазвичай `null`. З білдером створення об'єкта виглядає просто і зрозуміло.

**Мій сценарій:**
Я зробив клас `UserProfile` (профіль користувача). Суть така: при створенні профілю обов'язковими є тільки `id` та `email`. А всі інші штуки типу адреси, телефону чи аватарки — можна заповнити, а можна й пропустити. Замість того, щоб передавати купу null-ів у великий конструктор, я використовую `UserProfile.Builder` і викликаю методи тільки для тих полів, які реально хочу задати.
